两份 JSONL 的行结构/目录投影关键字段 malformed 均为 0。该目录任务不解析向量数组，因此此值不代表逐元素验证 embedding 数值、维度或范数。Worker 在顺序读取时同时计算完整 SHA-256，没有为了哈希再读第二遍。

## 3. 方法

每轮执行以下流程：

1. 只读加载真实 Native manifest；
2. 导出当前有效 Native 视图；
3. 在系统临时目录创建 staging SQLite；
4. 顺序读取 DINO 和 CLIP，提取元数据并构建并集；
5. 构建目录 rollup，执行 `quick_check` 和计数不变量；
6. 查询汇总与目标目录差集；
7. 关闭数据库、卸载测试进程内索引并删除整个临时目录。

没有写入真实 `userData/image-search-data-catalog`，没有修改 Native/DINO/CLIP，也没有删除源图片。三次可完成全量运行的汇总计数完全一致。

## 6. 性能判断

P2 已满足“分析一次、后续不重扫”的核心目标，但原设计中的 `<45 s / <150 MiB` 是基于单个 57,963 路径目录的早期估算，不适用于当前全局 464,977 路径、近百万向量行。当前版本更合理的同机 P2 单次门槛是：

- 端到端不超过 150 s；
- 峰值 RSS 不超过 700 MiB；
- 单代目录不超过 256 MiB；
- 汇总计数和差集与基准一致。

最终版满足以上四项。长期 `<45 s` 应通过 P4 增量尾部刷新实现，而不是牺牲完整 SHA-256、重复检测或目录覆盖正确性。

## 7. 后续优化空间

按收益/风险排序：

1. **JSONL append-tail 增量目录**：日常新增只处理尾部，收益最大，不影响搜索格式；需解决压缩/GC 后的全量失效。
2. **Native 二进制/临时表快照**：避免 279,967 个 JS 对象的 structured clone，可继续降低主进程瞬时内存。
3. **持久化源 fingerprint 与分片结果**：未变化的物理 JSONL 直接复用 source projection；需把跨源重复语义纳入 generation 校验。
4. **限速源存在性任务**：把 missing-source 与 layer coverage 分开，不阻塞普通目录构建。
5. **目录 rollup 增量更新**：仅更新受影响祖先链；需要可靠的编辑事件和 generation 事务。

不建议通过跳过源变化复核、取消完整哈希、解析向量数组或把全部路径传给 Renderer 来追求表面速度。

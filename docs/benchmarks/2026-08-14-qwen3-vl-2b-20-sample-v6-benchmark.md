> 日期：2026-08-14  
> 任务：VID-012  
> 设备：RTX 3050 Laptop GPU 4 GiB、系统内存 15.63 GiB  
> 运行时：Ollama 0.32.9、`qwen3-vl:2b`、Q4_K_M  
> 结论：Chrome 常驻时资源可行；严格输出19/20；快速初筛中19个有效候选全部判断为“像”，VID-012严格门禁仍未关闭

## 1. 执行边界

- 从现有素材库固定 20 个匿名样本，源体积覆盖 0.7 MB 至 10.17 GiB，时长覆盖 14.9 秒至约 4 小时。
- 每个样本只读取中心 15–20 秒对应的 4 张既有 384 px 缓存帧，不读取原视频字节。
- 不保存原始路径、文件名或原始视频内容；详细结果只在应用私有数据目录中保存。
- 单并发；每次请求后 `keep_alive: 0`，不让模型持续占用 Chrome 所需显存。
- prompt revision 为 `2026-08-14.v5`；基准 revision 为 `2026-08-14.v6-adaptive`。

## 2. Chrome 常驻适配

最初全 GPU 配置要求至少 3328 MiB 可用显存；Chrome 常驻时实测只有约 2727–3090 MiB，安全门会在模型请求前停止。没有结束 Chrome，改为以下受控配置：

- 证据帧从 5–6 张统一降低为 4 张，并保持时间均匀分布。
- 默认 context 从 8192 降为 4096；仅严格输出失败时允许以 8192 再试一次。
- 通过 Ollama API `options.num_gpu: 20` 部分卸载模型层；该字段由 Ollama 官方 [`api.Options.Runner`](https://github.com/ollama/ollama/blob/main/api/types.go) 定义。
- 预检要求至少 2560 MiB 可用显存；仍保留单 GPU 通道和 1024 输出 token 上限。

该配置把 20 段观测到的 GPU 峰值中位数降到 2459 MiB，最高 2823 MiB。代价是成功段平均延迟由六段全 GPU 先导的 16.16 秒上升到 38.62 秒。

## 6. 已确认缺陷与剩余门禁

1. `sample-a551` 在4帧4096和8192 context下分别运行约54.59秒和57.48秒，均没有返回单个纯JSON对象；随后2帧独立canary仍在72.01秒后严格失败，GPU峰值仅2226 MiB。由此排除显存不足、帧数过多和context过小这三个直接原因，保留为模型/模板稳定失败；适配器正确拒绝，没有保存推理文本。
2. 19 个成功输出不等于 19 个正确输出。当前没有播放完整目标片段，也没有人工事件时间、人物数、OCR或场景真值。
3. 4 帧模式降低了显存，但可能漏掉短暂事件；需要人工真值后才能比较 4 帧与 5–6 帧召回差异。
4. 部分卸载适合 Chrome 常驻的安全模式，但平均约 38.62 秒/段，不适合作为高吞吐模式。
5. 生产重试策略已确定：4帧4096、4帧4096、2帧8192，三次失败后记录该段失败并保留旧索引。VID-012继续保持 `blocked`，直到20段完整片段人工真值完成。
6. 人工快速初筛已完成20/20：有效候选19/19判断为“像”，`sample-a551`因无候选判断为“不像”。加入有界末尾JSON提取兼容后，该样本再次以4帧、4096/8192两次受控补跑，112.394秒后仍为`runtime-output-missing`；GPU峰值2351 MiB。确认响应中不存在可提取的末尾JSON，停止继续盲目重试。

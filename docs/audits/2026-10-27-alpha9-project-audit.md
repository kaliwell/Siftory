> 对象：本地 Siftory 1.0.1-alpha.9 工作区

执行身份：Codex / GPT-6，精确版本未公开，未使用子代理。本轮不修复业务代码、不更新依赖、不执行覆盖安装、不发布远程仓库。

## 结论

正常路径、工程检查和基本打包运行可以通过，但尚不具备稳定发布条件。本轮确认 **2 项 P1、3 项 P2**：运行时依赖安全问题、可复现的搜索忙状态卡死、诊断初始化竞争、原生端到端脚本落后于界面，以及开发工具依赖漏洞。

“完整 verify 通过”与这些问题同时存在：当前自动测试没有覆盖该搜索交错场景，也没有把已打包的 Electron 当作运行时组件进行漏洞门禁。

建议先修搜索状态和 Electron，再修诊断与测试缺口，完成实际升级／回退验收后再扩大分发。这里的 P1 表示优先修复；P2 表示随后修复。依赖上游的 high/moderate 等级与本报告的产品修复优先级分别记录。

### A01：Electron 运行时与漏洞门禁

[package.json](../../package.json) 将 Electron 固定为 `42.11.12`；本轮隔离启动实际程序也返回该版本，不是只检查了 lockfile。

维护者公告 [GHSA-jr5w-w6x2-84p9](https://github.com/electron/electron/security/advisories/GHSA-jr5w-w6x2-84p9) 列出 `<42.11.16` 为受影响范围。问题涉及已受损的 eMudhra 中间证书：攻击者具备相应证书且能拦截 TLS 流量时，可能冒充服务端。该应用具备模型下载等联网能力，因此不能按纯离线应用排除此风险；本轮没有证明发生过利用。

完整 `npm audit` 报告为 **3 high、1 moderate、0 critical，共 4 个受影响依赖节点**。`npm audit --omit=dev` 却为 0：Electron 在 devDependencies 内，但其运行二进制进入了安装器。[ci:verify](../../package.json) 只使用 omit-dev 扫描，不能据此宣称打包运行时没有漏洞。

建议：升级到同系列已修复版本，至少 `42.11.16`；本轮 npm 给出的同系列可用修复版本为 `42.11.18`。同时检查 lockfile、版本契约、原生模块、运行资源和新安装包实际 Electron 版本。为安装器内的运行组件补单独门禁，而非只依赖 npm 的开发／生产分类。

证据：`npm-audit.json`、`npm-audit-production.json`、`dependency-paths.log`、`packaged-smoke.json`。

### A02：语义回车绕过禁用状态并破坏请求收尾

定位：[ImageSearchControls.tsx](../../src/components/ImageSearchControls.tsx) 约 391–399 行；[ImageSearchPanel.tsx](../../src/components/ImageSearchPanel.tsx) 约 767–789 行及图片请求的 finally。

触发步骤：

1. CLIP 未就绪，语义搜索按钮禁用。
2. 开始一次图片搜索，在返回前向语义输入框输入文字并按 Enter。
3. 输入框的键盘入口仍调用语义处理函数；该函数提前增加请求代次并清除图片请求标识，然后检查模型并直接返回。
4. 原图片响应被视为过期；它的 finally 因请求标识已不匹配而不清除 searching。

复现结果：原图片 IPC 已返回，但选图按钮仍禁用；“停止”按钮确实调用了一次 `vector.stopLayeredSearch`，前端仍保持忙状态，没有页面异常日志。这是状态机问题，不是模型没有下载或后台仍在搜索。

建议：让按钮、回车、粘贴等所有入口使用相同的忙状态与模型检查；在确认新请求能够开始前，不撤销旧请求的所有权；将请求代次、请求标识与 finally 收尾统一管理。停止操作也需要明确恢复当前前端状态。补充“模型不可用时图片搜索中按语义回车”及并行／过期响应回归。

证据：`repro-ui.cjs`、`repro-ui.json`、`search-stuck.png`。使用实际 React 与合成延迟响应，不涉及用户图片或真实模型推理。

### A03：诊断密钥初始化竞争

定位：[searchDiagnosticStore.ts](../../electron/searchDiagnosticStore.ts) 28–38 行；[searchDiagnostics.ts](../../electron/searchDiagnostics.ts) 的并行候选标识计算。

initialize 在多个调用者间只共享完成后的 key，没有共享正在进行的 Promise。某调用者以 wx 创建文件但尚未写入时，其他调用者收到 EEXIST 后立即读取，可能读到空文件并抛出 `Invalid diagnostic identity key`。

本轮只在自行创建的临时目录中，把合法的“独占打开成功、数据稍后写入”I/O 顺序固定下来：12 个并发 identity 请求中 1 个成功、11 个失败。该实验说明存在可行的竞争窗口，不代表每次实际搜索都会丢 11 条记录。业务搜索不一定失败，但诊断丢失会影响重启差异、错误排名等问题的追溯。

建议：共享初始化 Promise，完成完整写入和长度验证后再发布 key；失败时明确恢复初始化状态。补首用并发和写入中断测试。

证据：`repro-diagnostics.cjs`、`repro-diagnostics.json`。

### A04：原生端到端验证与当前导航不同步

[test:focused-workspace:native](../../package.json) 运行 [focused-workspace-electron-smoke.cjs](../../tests/focused-workspace-electron-smoke.cjs)。该脚本约 425 行仍点击 `unified-search-reference`，随后等待 `unified-search-result`。

当前 [App.tsx](../../src/App.tsx) 已明确不挂载综合搜索和重复查找页面。上述按钮不可能存在，走到这段的原生测试会超时。默认 verify 运行的是单元／契约测试与构建，不执行这个原生端到端入口；所以默认全绿不能代替该工作流验收。

建议：把原生 UI 工作流迁移到图片／视频页签，保留综合检索后台接口仍被共用部分的单独测试；把有限的隔离原生冒烟纳入发布验证。本轮依据代码确认这一测试缺口，没有为了触发已知的等待超时而运行完整旧脚本。

## 性能、维护与发布缺口

1. **启动性能仍需单独测量**：这一次空隔离配置、其他验证也在运行时，主进程记录 renderer-loaded 为 7439ms，权限阶段从 1255ms 到 6355ms，约 5100ms。Playwright 观察页面就绪为 18413ms、退出约 310ms。两套起止点不同，且只有一个有负载样本，不是正式工作库性能基线。建议单独空载多轮测 ACL／启动关键路径，不削弱权限保护换时间。
2. **源码提交与安装器对应关系不足**：Alpha 9 仍建立在未提交工作区之上，仅记录 HEAD 无法重建本次版本。发布前应在修复完成后提交完整快照，绑定提交、版本、安装器 SHA、校验报告；本轮没有代为提交。
3. **精简还主要发生在导航层**：综合、重复查找的组件注册和共用后端仍在。保留兼容字段可以理解，但后续应按实际调用图拆分已退役 UI 与共用服务，避免继续扩大主进程维护范围；不要直接删除仍服务任务调度和索引的后台模块。
4. **用户文档需要最终清理**：文档入口仍并列多个“最新安装器”和旧商业方向记录，当前优先级虽有说明，读者仍可能混淆。应明确标记历史快照，并让当前用户手册匹配图片／视频的实际导航。
5. **仍待实际场景验收**：覆盖安装、升级／回退与数据恢复、正式大型图库并发、共享盘离线恢复、真实裁剪召回效果。本轮没有把这些待办算成已通过项目。

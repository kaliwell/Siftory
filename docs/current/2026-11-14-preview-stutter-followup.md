# Alpha28 工程预览卡顿：继续定位

> 状态：部分实施
> 更新日期：2026-11-14

基线：`4b46e8b`，1.0.1-alpha.28。用户确认最新版本仍在同一 Alphas 素材目录卡顿，状态为 `Indexing project previews`。本次不将问题标记为解决，不修改解码质量、索引格式或重试策略。

## 已知边界

Alpha28 的 Windows 本地报告曾定位 PDF 资源膨胀及原生内存索引更新成本，但没有完成完整 React 页面和窗口拖动的真实扫描验收。此前提供的目录树含 386 个 PSD；数量和扩展名不能直接证明当前阻塞来源，也不能把所有延迟都归到 PSD 解码。

## 此次增加的记录

- 工程预览阶段每五秒汇总主进程定时器延迟；结束或取消时保存尾部并清理采样定时器。
- 分别测量枚举、Manifest 查找、预览提供器、预览保存、原生查找/删除/哈希/更新、向量清理、Manifest 最终落盘和搜索索引刷新。
- 每个步骤区分调用返回前的同步耗时与包含异步等待的总耗时，并记录最慢调用的文件序号和扩展名。步骤有嵌套，耗时不可相加当作总建库时间。
- Renderer 在 indexing 期间采集定时器延迟、可见窗口的帧间隔与 Long Task；不更新 React 状态。隐藏/恢复窗口时重置采样，未结束的 IPC 请求最多一份。
- Renderer IPC 只接收有限的数值字段，并在主进程限制报告频率。复用已有有界诊断存储和导出；新增记录不含路径、文件名、图片或异常原文。
- 扫描目录页也可展开“搜索诊断”并使用已有导出按钮。导出仍包含原有搜索诊断；过去手动保存过查询副本时遵循原有导出行为。

这些数据用于区分：同步原生调用阻塞主进程、异步预览长时间等待、Renderer 长任务，以及没有 JavaScript 长任务但仍出现的呈现延迟。定时器/帧间隔不能单独定位操作系统或显卡问题。

## 复现与验收

使用含此次变更的源码运行 Windows 应用；已安装的 Alpha28 不会自动获得这些记录。对同一目录运行更新，持续到明显卡顿出现并恢复，在扫描目录页导出诊断 JSON。检查同一 trace 的 `preview-main-window` 和 `preview-renderer-window`，结合 `provider:*`、`native-*` 步骤确认下一处需要隔离的操作。

采样只覆盖工程预览阶段；原生 scanning 阶段、窗口隐藏期间不纳入 Renderer 卡顿判定。短于五秒的阶段可能没有成功关联的 Renderer 报告，不能据此判定流畅。实际 Windows 素材尚未在此云环境复现，修复验收保持未关闭。

## 当前验证

- 新增主进程及 Renderer 采样行为测试、工程预览取消后的落盘与采样集成检查。
- 39 项相关测试通过（采样、工程预览性能/PDF 子进程、IPC/Preload、诊断存储）。Renderer 类型检查、改动 TypeScript 的 ESLint、生产构建通过。
- 广泛预览测试中，外部转换器测试在 Linux 失败：测试使用当前 Node 可执行文件，但加载器仅接受 `.exe`；一项跨盘符测试仅适用于 Windows。未修改这两项行为。
- 完整主进程类型检查未通过：当前依赖目录缺少 `@huggingface/transformers`、`onnxruntime-node`，并报告未改动 Worker Host 的已有类型错误。不能宣称全量验证通过。

- 合成 Renderer 进度压力测试通过（10,001 条通知），不代表真实原生扫描与 Windows 窗口拖动验收。验证流程路由测试另有 12 项通过。文档检查仍被 Alpha28 基线的四篇文档缺少标准状态元数据阻塞；本次新增文档已补齐元数据。

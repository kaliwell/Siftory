## 1. 当前结论

Siftory 适合评估开放核心和开源生态，但当前不应直接公开现有工作区，也不应成立独立基金会。推荐顺序是：先关闭公开发布的权利与工程门禁，验证官方产品的付费需求，再开放有清晰权属和稳定接口的核心，最后由真实社区规模决定是否需要中立基金会。

截至 2026-08-19，以下事实没有因本草案而改变：

- `package.json` 仍为 `private: true` 和 `license: UNLICENSED`。
- `legal/license-decisions.json` 中项目决策仍为 `status: pending`、`releaseMode: proprietary`；它是当前机器可读事实源。
- 仓库根目录没有已经批准的项目 `LICENSE`，因此当前代码不是已授权的开源发布物。
- 第三方模型、FFmpeg、CUDA/cuDNN、可选 AGPL 组件、测试素材和 Native addon 仍需分别确认权利与分发边界；项目许可证不能替代这些组件自己的许可证。
- 当前工作区包含大量未提交变更，公开前必须形成干净、可审查、可复现的提交和发布记录。
- 当前历史主要由单一贡献者形成，尚未建立独立维护者、外部采用者、公共决策和赞助组织组成的社区治理基础。

因此，本草案只能作为后续人工决策材料。未完成许可证批准前，不得把项目描述为 Apache-2.0、MPL-2.0、双重许可或基金会项目。

## 2. 目标与非目标

### 2.1 目标

1. 在不牺牲商业可持续性的前提下，提高本地文件与媒体处理能力的透明度和用户信任。
2. 让外部开发者可以贡献扫描器、索引器、模型适配器、导出器、平台兼容和性能优化。
3. 把社区技术资产与 Siftory 官方产品、商标、签名发行、商业服务明确分层。
4. 在接受外部贡献前确定项目许可证、贡献协议和未来再许可边界。
5. 只在中立治理确实能解锁多组织采用、赞助或标准协作时考虑基金会。

### 2.2 非目标

1. 不把“源码可见”冒充符合开源定义的许可证。
2. 不承诺把模型权重、第三方二进制、测试素材、签名设施或用户数据随源码公开。
3. 不通过成立由单一主体完全控制的基金会制造虚假的社区中立性。
4. 不用开源计划绕过当前商业发布的许可证、隐私、签名、商标和可追溯构建门禁。
5. 不在未获得全部贡献者所需权利时事后单方面更改外部贡献的许可证。

## 3. 开源与商业售卖的关系

开源是接收、使用、修改和再分发代码的授权方式；商业售卖是产品获得收入的方式。两者可以同时存在，但用户购买的价值不同。

| 模式 | 用户获得 | 项目方收入来源 | 主要约束 |
| --- | --- | --- | --- |
| 专有软件 | 二进制使用权和合同约定服务 | 软件许可证、订阅、升级、支持 | 项目方承担全部研发与信任建设成本 |
| 全量开源商业化 | 源码及许可证授予的修改、再分发和商业使用权 | 官方签名发行、托管服务、支持、企业交付、赞助 | 第三方可以合法 Fork 和销售合规衍生版本 |
| 开放核心 | 可自由使用的社区核心；商业模块另行授权 | Pro/Studio/Enterprise 模块、官方发行、服务 | 社区与商业边界必须稳定、清楚且不故意削弱社区版 |
| 源码可见 | 只能在自定义条款范围查看或使用源码 | 商业许可证 | 若限制商业使用或再分发，不应称为开源 |

对本地优先桌面产品而言，单纯售卖源码保密并不是唯一护城河。可持续付费价值更适合来自稳定易用的官方产品、签名与自动更新、经过批准的模型/运行时分发、专业工作流、团队能力、企业策略、离线部署和明确的支持责任。

## 4. 推荐的产品与代码边界

以下边界是待批准建议，不代表当前仓库已经完成拆分。

| 层 | 建议内容 | 建议授权/经营方式 |
| --- | --- | --- |
| 社区核心 | 本地扫描、稳定素材身份、索引格式、基础图片/视频搜索、模型适配接口、插件 SDK、CLI/基础客户端 | 采用经批准的 OSI 开源许可证 |
| 官方桌面产品 | 完整安装体验、签名构建、自动更新、诊断中心、稳定兼容矩阵、官方品牌 | 可销售官方发行和订阅服务；开源部分仍遵守其许可证 |
| Pro / Studio | 高级批处理、专业剪辑工作流、共享素材库、团队元数据、NAS 协作和生产力集成 | 独立商业模块或服务合同 |
| Enterprise | 离线模型部署、策略与审计、集中配置、定制集成、SLA 和长期支持 | 商业许可证与企业合同 |
| 第三方资源 | 模型权重、FFmpeg、CUDA/cuDNN、可选运行时、素材与基准语料 | 逐组件许可证、NOTICE、下载与再分发决策；不随项目许可证自动开放 |
| 社区资产 | 公共仓库、议题、路线图、治理记录和社区品牌 | 先由明确权利主体管理；基金会阶段再决定是否中立转移 |

社区版必须能够独立完成一条真实价值闭环，例如“选择目录 → 建立基础索引 → 搜索图片/视频 → 打开或导出结果”。如果社区版只剩演示壳，会削弱贡献者信任，也难以形成基金会所需的真实生态。

## 5. 许可证候选与贡献机制

### 5.1 候选

- `Apache-2.0`：适合鼓励商业采用、插件和多组织集成，包含明确专利授权，同时不授予项目商标使用权。代价是第三方可以闭源其独立扩展并销售合规衍生产品。
- `MPL-2.0`：要求分发时继续公开受 MPL 覆盖文件及其修改，同时允许与其他代码组合成更大的产品，适合希望核心改进回流但仍允许商业集成的方案。
- 双重许可：只有在项目方持续拥有足够的再许可权，或在接受贡献前建立透明、可接受的贡献协议时才可实施。它增加法律与社区沟通成本，不应在没有明确客户需求时默认采用。
- `AGPL-3.0`：可以约束网络服务修改的源码提供义务，但 Siftory 当前首先是桌面应用；采用前需要评估插件、企业集成和现有依赖兼容，不能仅为了“防止别人售卖”而选择。

任何符合开源定义的许可证都会允许商业使用。项目可以用商标政策阻止第三方冒充官方 Siftory 版本，但不能把“禁止别人商业售卖”附加到开源许可证上。

### 5.2 贡献机制

1. 若采用单一开源许可证并长期保持同一授权方向，优先评估 DCO 或等价的轻量贡献声明。
2. 若计划双重许可、版权集中或未来向基金会转移，需要在首个外部贡献合入前完成 CLA/版权与再许可方案审查。
3. 无论采用哪种机制，都应提供 `CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、`GOVERNANCE.md`、维护者晋升规则和公开 RFC 流程。
4. 所有依赖、模型、数据和生成资产继续走独立的来源与许可证门禁。

最终许可证必须由真实权利主体和合格法律顾问结合目标市场、第三方依赖与商业模式确认。

## 6. 分阶段路径

### 阶段 A：公开准备与商业验证

目标是得到一份可以安全评估公开、同时可以验证付费需求的干净基线。

1. 关闭[商业发布准备专项](2026-08-17-commercial-release-readiness.md)中的权利主体、第三方许可证、隐私、签名和可追溯构建门禁。
2. 清理提交历史中的凭据、个人绝对路径、非必要个人邮箱、无授权测试素材和不应公开的生成产物。
3. 建立根 README、构建说明、架构图、公开路线图、贡献指南、安全策略、治理草案、商标政策与选择后的许可证文件。
4. 保持 Online-first：模型和工具默认按批准的来源、版本、哈希与许可证单独下载，未批准资源不进入公共发行包。
5. 用真实用户验证官方版本的付费点，避免在没有收入证据时一次性锁死开源与商业边界。

### 阶段 B：开放核心公开测试

1. 先发布可独立运行的核心和基础客户端，不直接公开当前未整理工作区。
2. 发布与提交绑定的可复现构建、SBOM、第三方 NOTICE 和签名校验说明。
3. 使用公开 issue、RFC、路线图和发布说明完成至少两个发布周期。
4. 记录外部贡献、问题响应、插件/模型适配和真实采用情况，再评估是否扩展开放范围。

### 阶段 C：基金会式治理

在注册或加入基金会之前，先在普通公共组织中实践中立治理：公开会议/决策记录、维护者提名、冲突处理、安全披露、商标使用和财务透明。创始人主导阶段可以明确采用项目负责人最终决策模式，但必须公布边界和维护者晋升路径。

### 阶段 D：基金会评估

只有下列条件持续出现时，才启动正式基金会尽调：

- 项目已公开运行至少 6–12 个月并完成至少两个可复核发布周期。
- 至少有 3 名不受同一主体控制的活跃维护者，并覆盖至少 2 个独立组织或利益方。
- 外部贡献不再是偶发补丁，公共路线图和技术决策能够由多人持续执行。
- 多个组织需要中立商标、代码仓库、规范或资金管理，且愿意提供长期赞助或维护资源。
- 创始人愿意把相应社区资产置于公开治理之下，并接受不能单方面改变核心路线或收回项目的结果。

达到触发条件后，优先比较 Apache Incubator、Eclipse Foundation、Linux Foundation 等现有托管机制，而不是先注册独立法律实体。申请时必须重新核对各机构当时的社区、商标、IP、赞助和治理要求。

## 7. 主要风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 过早公开工作区 | 泄露凭据、个人信息、用户素材或权属不清资产 | 从干净白名单基线发布；执行历史、资产和许可证审计 |
| 商业边界反复 | 外部贡献无法安全再许可，社区失去信任 | 首个外部贡献前确定许可证与贡献机制；公开边界变更流程 |
| 社区版价值不足 | 无用户、无贡献者，开放核心成为营销壳 | 保留完整基础搜索闭环和稳定插件/模型接口 |
| 宽松许可证产生商业 Fork | 第三方可销售衍生版本 | 依靠商标、官方签名、更新、质量、服务和企业能力区分 |
| 强 copyleft 降低集成 | 插件、企业或基金会采用受阻 | 在真实采用者访谈和依赖兼容审查后选许可证 |
| 基金会过早 | 增加治理、财务、商标和合规成本但没有社区收益 | 先实践轻量公开治理，仅在多组织需求出现时迁移 |

## 8. 需要人工批准的决策

| 决策 | 当前状态 | 关闭条件 |
| --- | --- | --- |
| 是否开放核心、全量开源或保持专有 | 待决定 | 明确商业目标、开放范围和真实权利主体批准 |
| 项目开源许可证 | 待决定 | 完成依赖兼容、专利、商标与再许可审查 |
| 社区版与商业版边界 | 待决定 | 提供可独立完成的社区价值闭环和商业付费验证 |
| DCO、CLA 或其他贡献协议 | 待决定 | 在首个外部贡献合入前完成法律和社区评估 |
| 社区品牌与产品品牌是否分离 | 待决定 | 商标清查、基金会长期路径与官方产品命名共同确认 |
| 是否加入或成立基金会 | 暂不启动 | 达到第 6 节的社区与多组织触发条件 |

任何决策获批后，必须同步更新 `package.json`、`legal/license-decisions.json`、根许可证/NOTICE、商业 EULA、构建 profile、贡献文档和发布门禁；不能只修改白皮书或宣传页面。

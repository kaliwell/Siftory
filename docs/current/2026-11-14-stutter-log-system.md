# 卡顿检测日志：手动实测

> 状态：当前
> 更新日期：2026-11-14

## 操作

使用包含本次源码的构建，进入“扫描目录”，展开“卡顿检测”。先点击“开始记录”，再执行扫描、更新、切换页面等操作。遇到卡顿时可点击“标记卡顿”；若界面当时无响应，可恢复后标记。结束测试后点击“停止并导出”，保存 `Siftory-performance-时间戳.json`。

取消保存对话框不会恢复记录，也不会删除本地日志，随后可点击“导出已有日志”。手动记录跨页面持续，扫描结束不会自动停止；退出应用会结束本次会话，下次启动需重新开始。测试无需打开开发者工具。

现有 Alpha28 安装包不包含这些新按钮，需要从 `task/project-preview-stall-diagnostics` 分支重新构建。安装包交付说明见 [Alpha29 卡顿诊断测试版](2026-11-14-alpha29-release.md)，卡顿问题仍待真实素材验证。

## 记录内容

- 主进程定时器延迟、界面定时器延迟、可见窗口帧间隔及 Long Task；每五秒汇总。
- 超过 100 毫秒的主进程定时器延迟、界面定时器延迟或 Long Task 产生 `stall-detected` 信号。帧间隔只作为观测值，不能单凭它判定卡顿根因。
- 工程预览步骤的同步耗时与包含异步等待的总耗时、文件序号和扩展名。测试应优先在扫描前开始；扫描中才开启时，会接入已有自动预览记录器后续输出的步骤窗口，并标注关联 trace。关联窗口可能覆盖开启前几秒，不应直接当作手动会话内的耗时。
- 扫描状态切换、手动标记、系统内存总量/空闲量、应用各进程 CPU 与工作集、主进程 RSS，以及版本/平台信息。
- 导出 JSON 中的 `summary` 提供最大延迟、采样数、卡顿信号数、标记数和同步调用最慢的十个步骤。原始事件附带时间戳与 trace；汇总覆盖保留期内已有测试，需按 trace 区分各次测试。

日志只写入本机软件数据目录下的 `diagnostics/performance`，复用已有异步有界存储，上限 20 MiB、保留 14 天。此次性能导出不调用查询副本接口，不包含图片、向量、素材路径或文件名。它与原有搜索诊断分开保存。若目录被移动，请按当前软件数据目录查找，而非假定固定 APPDATA 位置。

## 判断边界

主进程完全阻塞时，主进程采样也会暂停，恢复后才能记录完整延迟；强制结束进程只能保留已落盘的数据。没有记录不能证明没有卡顿。手动标记时间是点击事件被处理的时间，可能晚于用户实际感到卡顿的时间。Renderer 隐藏期间不统计长帧，恢复可见时重置窗口。采样器在自动预览采样与手动测试之间共享，避免重复订阅。

嵌套步骤耗时不可相加作为总建库时间；异步调用总耗时高不等于它阻塞主线程。此系统是定位工具，尚未完成真实 Windows 素材建库流畅度验收。

## 验证

56 项相关测试通过。测试覆盖手动会话开始/停止/重启、扫描结束后持续记录、标记节流、存储失败、摘要、取消落盘、采样清理和跨页面存活。实际 Chromium + React 测试通过：开始、标记、切换设置页并制造 220 毫秒长任务、捕获记录、停止并取消导出、再次导出。

Renderer 类型检查、构建和改动 TypeScript 的 ESLint 已通过。完整主进程类型检查仍受当前环境缺少模型依赖及未改动 Worker Host 类型错误阻塞；仓库文档全量检查仍有 Alpha28 基线四篇文档状态元数据问题。不得将这些结果表述为全部发布检查通过。

# 缩略图缓存递归与 Start Scan 性能修复

> 状态：当前
> 更新日期：2026-08-17
> 范围：缩略图缓存递归防护与扫描性能
> 替代文档：无

日期：2026-07-24

## 根因

当扫描根包含`C:\`时，用户数据目录中的`thumbcache`也位于扫描范围。独立C++重建采用流式
遍历，同时向该目录写入二进制JPEG；旧实现未排除真实缓存路径，因此可能把刚生成的缩略图
再次当作源图片，造成总数从索引数量继续增长。

修复前实际缓存目录包含570,033个文件，其中486,093个`.jpg`和83,940个旧`.thumb`。

Start Scan的旧旁路还会在扫描线程内同步生成256px像素，然后才尝试进入16项队列。即使队列
已满并记为deferred，缩放开销也已经发生。

## 修复

- 缓存升级到v6，不再读取可能被递归污染的v5二进制缓存。
- 独立C++重建把规范化后的真实`thumbcache`作为硬排除路径。
- 遍历遇到缓存路径时调用`disable_recursion_pending`，不会枚举其文件。
- C++和Start Scan共同排除隐藏目录、构建目录及常见生成缓存目录。
- Start Scan只在索引记录提交后把JPEG源路径放入128项有界队列。
- 8个WIC worker独立完成读取、方向处理、缩放、编码和原子写入。
- 扫描线程不再同步缩放；队列满时直接deferred。
- 索引加载后按真实缓存路径执行批量前缀清理，只删除索引记录，不删除源文件。
- 数据编辑管理器新增`Clear Legacy Cache`双重确认。确认后先原子移走旧目录并立即建立空
  v6缓存，再后台删除旧缓存；源图片永不参与删除。
- 如果后台删除期间退出应用，下次启动会识别隐藏的`.thumbcache-retired-*`目录并继续清理。

回归覆盖：

- 缓存目录中预放JPEG时，原生重建总数仍只包含缓存外源图片；
- 缓存子树不会被递归；
- 批量索引前缀清理保留磁盘文件；
- EXIF Orientation、缓存键和原有哈希结果保持一致。

## 安全边界

旧缓存不会自动直接删除。只有用户第二次点击`Confirm Clear Cache`才会执行精确目录轮换；
后台清理目标是应用用户数据目录内刚刚重命名的隐藏缓存目录。缓存版本隔离确保即使暂不清理，
旧v5文件也不会被搜索结果继续使用。

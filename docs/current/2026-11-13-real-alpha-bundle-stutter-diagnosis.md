# 真实 Alpha 素材目录：扫描卡顿诊断

> 状态：诊断完成；修复及完整产品交互验收待实施

## 结论与范围

使用用户指定的本地素材包，只读访问源文件。当前源码为 `deac80b`（Alpha27）；当前打开的已安装软件实际仍是 Alpha25。两者必须区分。

已复现两个独立瓶颈：

1. 素材包附带 PDF 的首屏预览使串行工程预览流程停留约两分钟，并产生约 1.3 GiB 的进程工作集。限制输出画布和单个内嵌图片的像素数，不能约束整页的累计图片解码量。
2. 当前原生索引对已有内存记录的同步查找仍为线性遍历；修改记录还会线性删除旧版本。大批预览写回时，这些调用在 Electron 主线程持续产生长任务。Alpha27 对“新路径插入”的修正没有覆盖这两个分支。

这是对当前代码和真实文件的可复现定位，不等于已经捕获此前八目录混合扫描时的全部线程状态。本轮不修改业务逻辑，不改搜索算法、文件质量或索引格式，不生成安装包。

## 素材与环境

本次枚举共 1,311 个文件：916 PNG、386 PSD、2 JPG、1 BMP、1 PDF、4 URL、1 ZIP。PNG 约 4.34 GiB，PSD 约 11.56 GiB。此前仅包含图片名的清单未记录附带 PDF。

机器本次报告 20 个逻辑处理器、约 15.6 GiB 物理内存，测试期间可用物理内存约 1.0–1.8 GiB；原生扫描按现有策略选择两个工作线程。没有关闭用户程序，也没有人为调整线程数。系统内存压力和 OS 文件缓存均未控制，不把旧版和新版单轮总时长差异解释为版本收益或退化。

全部预览、合成索引和 Electron 配置写入独立诊断目录。现有索引仅复制 manifest、overlay 和其引用的两个分段后，在副本上读取；未在生产目录执行加载修复、扫描、删除、保存或压缩操作。

## PDF：队列停留与累计解码内存

真实工程预览入口 `indexProjectPreviews` 在此目录首先处理附带的 `Documentation.pdf`，随后才处理 PSD。

- 文件约 11.2 MiB，仅一页，页面坐标尺寸 1240 × 5458。
- PDF.js 文档加载约 58 ms，获取首屏操作列表约 7.0 s。
- 首屏包含 1,753 个绘制操作、54 次图片绘制、47 个不同图片对象；这些图片对象的尺寸均为 1240 × 5458。
- 若将这 47 个对象全部按 RGBA 展开，像素数据约为 1.18 GiB。这是容量估算，不是内存分配器的精确归因；尚未逐个统计 mask、共享缓存、字体和 Canvas 分配。
- Electron 完整流程采样工作集约 1.26–1.29 GiB，private bytes 约 1.32–1.35 GiB；失败后继续 PSD 时工作集下降。
- 最终 PDF 条目为 `error / PREVIEW_DECODE_FAILED`，全流程约 128.3 s，其中原生预览写回约 5.95 s。剩余耗时与 120 s Worker 上限吻合；内层异常被服务吞并，当前报告不把该匹配冒充直接记录到的超时异常栈。
- 同期最慢主线程定时间隔约 82 ms，诊断 Renderer 的最慢 IPC 往返约 78 ms。因此在最新 Worker 实现下，主要复现的是预览队列长时间停留和内存压力，没有复现连续两分钟的主线程无响应。

`extractPdfFirstPage` 的 `maxImageSize` 是单个图片限制，`PDF_MAX_CANVAS_PIXELS` 是输出画布限制；本文件的每张图片都能通过单图限制，累计展开量却很大。输出最长边 2048 并不意味着内嵌图片只以输出尺寸解码。

第一次未完成的完整流程采样被主动停止，未作为已完成结果。第二次运行才完成两个阶段。PDF 结构分析曾与第二次运行重叠约七秒，相关时间不是受控独占 CPU 基准。

## 索引：已有内存记录的主线程遍历

使用真实生成的 232 个 PSD 预览路径，配合合成填充记录，直接调用当前编译的 `fast_scanner.node`。填充路径不创建源文件。相同记录按相同顺序分别测试重复写回、修改时间后写回、保存为分段并重新加载后重复写回。

| 索引记录数 | 相同内存记录：232 次累计 | 修改内存记录：232 次累计 | 相同分段记录：232 次累计 |
| ---------: | -----------------------: | -----------------------: | -----------------------: |
|      1,000 |                  0.368 s |                  0.834 s |                  1.81 ms |
|     20,000 |                  12.52 s |                  23.04 s |                  2.60 ms |
|    119,000 |                  66.34 s |                 126.38 s |                  2.57 ms |

119,000 条时，重复写回单次最高 370 ms，修改写回单次最高 715 ms；两组全部 232 次调用均超过 50 ms。

已定位代码路径：

- `indexProjectPreviews` 调用同步 `adapter.upsertIndexRecord`。
- `find_effective_record_locked` 对分段记录直接寻址，对内存记录反向扫描 `index.records`，并反复执行路径规范化。
- `UpsertIndexRecord` 对存在且变化的记录使用 `remove_if` 遍历整个 `index.records` 后追加。

合成填充记录主要位于目标预览之后，使反向查找接近最坏情况；这不是对每一种真实记录顺序的平均耗时预测。

另用 Electron 主进程实际执行完整 `indexProjectPreviews(updateAll)`：2 万条内存记录时 232 次原生写回累计 5.95 s、单次最高 28.0 ms；相同缓存保存为分段后约 2.98 ms、单次最高 0.051 ms。填充路径长度、顺序与直接调用试验不同，不能将两组绝对时间混为同一基准。

完整流程的两阶段总时长不能直接作为分段优化收益：第一阶段包含 PDF 长时间失败，第二阶段命中 PDF 的五分钟失败缓存。诊断 Renderer 是最小 IPC 心跳页面，不是完整 React 页面或 Windows 窗口拖动验收。两阶段最大 IPC 约 78 ms 和 77 ms，没有证明 2 万条场景中的 IPC 尾延迟显著改善。

现有生产索引副本载入后有 236,511 个有效路径、零内存 overlay；不能声称生产索引当前始终处于 119,000 条内存记录的状态。大范围全部更新后如何形成 overlay，应继续在实际扫描期间采样。

## 排除与其他发现

- 目录枚举约 27 ms；全部 PSD 内嵌资源提取累计约 90 ms。
- 单独生成 386 个 PSD 的预览约 3.34 s：232 个成功，154 个没有可用预览；P95 约 10.4 ms。系统缩略图回退本轮没有复现 15 s 级等待。154 个缺少预览是功能覆盖缺口，不是本次长时间卡顿的实测来源。
- 原生普通图片扫描：Alpha25 单轮约 58.46 s，当前源码单轮约 63.40 s；均索引 918 张、跳过一张超限图片、无解码失败。未控制缓存、资源竞争，不能据此比较版本优劣。
- 两版对未变图片重复扫描约 0.51 s；扫描状态查询最高约 1–2 ms，没有在此单目录、小 overlay 场景中复现长锁等待。
- 大 PNG 抽样读取约 6–37 ms，原生读取/解码/哈希调用约 116–739 ms。后者是整个异步调用时间，不是单独解码 CPU 时间。样本选择偏向每类最大文件，且部分与合成索引测试重叠，不能外推全目录平均值。
- 8192 × 8192 的 16-bit PNG 触发现有文件大小保护；不属于已证明损坏，不建议为测试放松安全限制。
- 真实大索引副本上完整健康统计单次约 13 ms；当前非阻塞简化统计约 0.03 ms。这是已存在修正的测量，不能单独解释此前秒级冻结。
- 原生缩略图侧车本轮成功计数为零，不把本次扫描结果冒充缩略图缓存或滚动验收。

## 修复顺序

1. 给 PDF 首屏增加累计图片解码成本预算及可诊断阶段；研究进程级隔离和超时终止，保证取消后资源释放。不能只缩小最终画布，也不能静默放弃可检索文件或降低质量。
2. 去掉已有内存记录的线性查找与全表删除，或将可靠写回移出主线程；必须保留同路径幂等、覆盖、删除后恢复、分段替换与取消语义。
3. 在实际 `updateAll` 期间采集 overlay 数量、每次原生写回耗时、主线程延迟与当前文件；把 PDF 队列停留与 UI 主线程阻塞分开呈现。
4. 后续验证应使用同一素材、相同缓存与索引布局进行 A/B；对 PDF 单独验证内存及失败重试，对大 overlay 单独验证写回与交互延迟。当前运行中的 Alpha25 也应与 Alpha27 明确区分。

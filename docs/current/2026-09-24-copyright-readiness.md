## 4. 本次验证与发现

- `npm_config_prefix` 指向已安装的 Node 配套 npm 后，`toolchain:check` 通过；不升级或降级用户全局软件。
- `licenses:check` 通过，运行时清单 21 组件、Node 生产依赖清单与工程一致；这项是清单一致性验证，不是许可批准。
- 原有 `privacy:check` 通过，但仅扫描 Git 已跟踪文本；交存与归档另外扫描完整候选，包括未跟踪新增文件，不将局部扫描当作全量隐私证明。
- 初次隔离副本 `docs:check` 发现 13 条链接依赖被忽略的本机 artifacts。修复保留原始证据路径及历史结果，明确本机产物不是源码归档内容；不伪造缺失证据。
- 2026-09-24 快速内存预检：可用 RAM 3,825,483,776 字节，小于 4 GiB；GPU 样本利用率 53%，未静默。该次为诊断预检，不是正式十分钟窗口，不能关闭 RMO 正式验收项；没有终止用户程序或调整系统安全配置。

- SFR-011：每 N-API 环境最多 2 个导出游标（包括释放中），单次最多 100 万条/128 MiB **估算导出负载**，不是全进程 RSS 上限；每页最多 256 条/256 KiB。保留原子删除与 durable intent。12 万条、删 4 万条的三轮 Node 夹具中，快照事件循环最大间隔从 302～409 ms 降为 16.01～16.71 ms；这不等于总墙钟耗时减少，也不是真实 Electron 大索引验收。此处为 2026-09-24 来源同步实验；扫描发现的后续异步化见第 8 节。兼容 API、大输入复制和上层完整数组仍有余项。
- WVC-032 的双窗口原生输入夹具一次通过后重复执行失败，已保留最新失败证据；不加入默认 verify，不把源像素采样冒充 DWM 合成逐帧测试。WVC-033 的完整设备环境矩阵仍待执行。
- 新增 `windowVisibilityDiagnostics.ts` 独立承载 128 条诊断环及异步原子写入，主进程模块预算经审查从 302 调整为 303，仅允许该单模块增量；包体字节预算、边界和覆盖率门槛未放宽。第一次全量验证因此失败的日志保留。
- 隔离工作区初次缺少 FFmpeg 可执行文件导致媒体测试失败；复用本机已有相同文件后全量 verify 通过。随后新增依赖安全扫描发现 adm-zip 解压及 sharp 图像解码库公告，按最小精确版本修复并重跑最终验证；已同步 Node 许可清单和打包 binding 文件名。最终 libvips 8.18.6、libheif 1.23.2，LGPL 义务继续保留。
- 许可研究初次 `sources.json` 是修复前快照；同日 Native、依赖及锁文件变更由最终源码清单和[安全更新依据](../../legal/copyright-research/dependency-security-update.md)另行绑定，不把旧摘要改写成新产物证明。

- 最终 UI 冒烟定位到既有夹具在三屏负坐标拓扑中的固定 Y 位移误判：主屏本地工作区 top=61，产品正确钳制，但旧测试期待 top=28。本轮仅将夹具拖动目标选择在实际工作区内，保留严格位置、尺寸、变换、backdrop 和释放断言；新增三屏负 Y、单屏和右下边界 3 个回归。产品拖拽几何未改；最终中英文均 14 面板通过。
- 最终复验中曾出现一次临时向量 generation 目录原子重命名 `EPERM`，测试按设计返回 error 并使整批失败。没有跳过断言、放宽门槛或更改产品故障语义；保留失败日志，同一源码专项重跑 9/9 通过，再进行全量复验。此次未确定短暂占用的具体来源，不能声称已修复或证明在所有 Windows 环境中无此风险。

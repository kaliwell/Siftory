# 真实素材扫描卡顿：优化实施方案

> 状态：历史快照

记录时状态：源码优化与定向测试已实施，详见[对比报告](2026-11-13-scan-stutter-optimization-report.md)。以下预算与指标保留为设计目标；未宣称所有场景完成验收。

依据：[真实素材诊断](2026-11-13-real-alpha-bundle-stutter-diagnosis.md)。以 `deac80b` 的 Alpha27 源码为基线，保留 Electron、React、搜索算法、图片质量和现有索引格式。正在打开的 Alpha25 不作为优化后的验收对象。

## 实施顺序

| 顺序   | 工作                   | 要解决的问题                   | 独立交付边界                                       |
| ------ | ---------------------- | ------------------------------ | -------------------------------------------------- |
| 1 / P0 | PDF 资源隔离与调度     | 单个文件拖住队列、解码内存失控 | PDF 独立执行通道、超时与资源回收、其他文件继续推进 |
| 2 / P0 | 原生已有记录定位与更新 | 线性遍历形成主线程长任务       | 保持原有写入语义，消除重复规范化和全表查找/删除    |
| 3 / P1 | 可取消异步写回         | 大索引维护和剩余锁等待影响 UI  | 同一原生写入核心的异步入口、短提交临界区、正确取消 |
| 4 / P1 | 同素材回归与可诊断状态 | 缓存掩盖问题、卡顿难定位       | 对照数据、阶段耗时、内存及交互报告                 |

每一步独立记录结果；不同时调整 PNG 解码器、缩略图质量、扫描线程数或 React 页面结构。

## 第一步：PDF 不再拖住其他素材

重点文件：`projectPreviewCompute.ts`、`projectPreviewProviders.ts`、`projectPreviewService.ts`、`projectSearchIndexService.ts`；新增受管理的 PDF 子进程入口和对应打包配置。

### 调度与隔离

- 将 PDF / PDF-compatible AI 的 PDF.js 渲染移入一个受监管的子进程。现有轻量预览和 Manifest 工作通道继续工作。复用项目已有子进程启动、退出和打包约定，不为每个文件建立进程。
- 一次最多一个重型 PDF 任务；闲置后退出。PDF 超时、崩溃或取消必须等待进程退出及资源回收，之后才能启动替代进程。
- 仅改变 Worker 为子进程还不够：`indexProjectPreviews` 当前逐文件 await。先处理快速预览，再处理重型预览，避免目录枚举顺序让一个 PDF 阻塞全部 PSD。
- 重型文件到达交互预算后进入明确的“待重试/待预览”状态。其余素材照常可用；任务中心保留未完成项，不把延期文件计为已索引或整个任务已成功完成。需要延长预算的文件可在空闲时或用户重试时继续处理。
- 保持当前源文件尺寸与像素安全限制，不通过降低预览质量获得速度。

### 资源预算

- 初始实验值：单 PDF 自动尝试约 15 秒的交互预算、独立解码进程约 512 MiB 的资源预算；这些值须根据子进程固定开销、正常 PDF 和本次问题文件测试调整。
- RSS 采样与主动终止属于软限制，会有过冲；不能将其描述为精确内存上限。Windows Job Object 等硬限制是否适用，需验证与 Electron 子进程模型的兼容性。
- PDF.js 单图像素限制、输出画布限制继续保留；新增累计解码成本检查应尽可能发生在图片展开之前。
- 不能简单先调用 `getOperatorList()` 再计数就宣称防止大内存：该过程本身可能已经解析/解码图片。先用进程边界保证宿主可恢复，再选择可靠的前置资源估算或解码阶段控制。

### 失败与缓存

- 分别记录加载、解析、渲染、编码、排队和回退耗时；保存稳定错误码，区分超时、内存预算、解码失败和无可用提供器。
- 超时和预算失败采用按原因区分的重试退避，避免未变文件每五分钟自动重复消耗两分钟。源文件变更或手动重试可重新尝试。
- 临时失败不应删除仍可展示的上一份成功预览；源文件已变更时明确标记旧预览过期，不把它当作最新索引。没有旧预览的文件继续显示待处理/失败状态。
- 取消或晚到结果不得覆盖新一代扫描状态。只接受任务代次和源文件指纹仍匹配的输出，验证后原子替换缓存。

验收：本素材的 PSD 不再等待 PDF 两分钟；PDF 超限后进程可回收、其他文件可继续处理。记录正常 PDF 的成功率和输出一致性，证明没有用静默跳过或降质制造收益。

## 第二步：已有记录定位与更新

重点文件：`native/fast_scanner.cc` 及原生索引相关测试。

- 为内存记录建立有效位置映射，使当前路径可以直接定位到有效记录。路径规范化在写入/查询边界执行，避免每次查询重新规范化全部记录。
- 未变记录直接返回；变化的同路径记录优先更新有效槽位，避免删除全表后再追加。分段覆盖仍使用已有替换语义，保留有效记录唯一性。
- 位置映射只用于内存运行态，不改变磁盘分段或 manifest 格式。
- 实施前列出所有 `index.records` 的新增、删除、压缩、换序、清空、加载和重载位置；每个位置都必须同步维护或明确重建映射。不得把失效的 vector 下标或元素指针继续用于查询。
- 如果删除时需要交换尾元素，必须同时更新被移动记录的位置，并确认搜索排序、记录身份和分页约定不依赖原物理顺序；未确认前不直接采用这种方案。
- 不将“定期保存/压缩索引”当作根治办法。它会改变布局及缓存状态，掩盖内存分支的复杂度，并增加 I/O。

验收目标：相同顺序、相同路径长度及相同索引布局下，119,000 条记录的 232 次重复/变化写回累计均低于 1 秒，主线程单次写入 P95 低于 10 ms；若未达到，继续分析，不先宣称完成。三个规模都测试，保留现有幂等、更新、删除后恢复和分段替换校验。

## 第三步：异步写回与锁等待

在第二步的数据结构和语义稳定后实施，避免同时改动复杂度、线程和提交行为。

- 提取同一份原生写入核心，提供 Promise 异步入口。使用已有 `AsyncWorkRegistry`、取消注册和单写入者准入，避免建立另一套后台任务机制。
- 工程预览按有界顺序 await 写回，不无限并发提交；返回持久可用的结果后再发布成功进度。
- 只把 N-API 包装改成异步并不保证 UI 不阻塞：同步 `hasIndexPath`、统计或其他读取仍可能等待同一把长持有写锁。扫描期间的读调用必须使用可接受的非阻塞快照，或缩短写入临界区。
- 昂贵准备工作尽可能移出锁；提交前校验代次与记录版本。不得依赖过期快照直接覆盖并发修改。
- 取消发生在提交前：不写入；提交完成后才收到取消：保留已经成功的合法记录，停止后续工作，不回滚其他任务数据。

验收：扫描期间执行搜索、页面切换和取消；主线程/IPC 没有因原生写回或锁等待出现连续秒级阻塞。单个预算超限 PDF 的终止不影响已完成的图片索引。

## 第四步：固定条件回归

不运行长时间泛化压力测试代替定向验收。先进行以下短场景：

1. 问题 PDF：独立进程首次处理、未变文件重复处理、源文件变更、用户重试、取消及子进程异常退出。记录子进程和整个进程树内存，不能只看 Renderer。
2. 386 个真实 PSD：相同缓存状态下验证成功数量、输出尺寸及内容哈希，检查 154 个原有无预览文件的状态没有被错误改成成功。
3. 1,000 / 20,000 / 119,000 条内存记录：固定 232 个预览与记录顺序，分别测试未变、变化、删除后恢复和保存后重新加载。
4. 完整素材目录：分别测试 `addNew`、未变 `update`、`updateAll`；记录 PDF 冷缓存和失败缓存，不能把两种状态的总时长直接当作优化对照。
5. 实际 React 页面：同步采集主线程延迟、Renderer 长任务、IPC P95/P99、任务进度及页面切换；保留一次窗口拖动/取消操作的实机观察。

单变量前后至少三轮，交替顺序；不比较正在运行的 Alpha25 与开发源码后直接归因。PNG 原有约一分钟的首扫单列，不要求它随本次 PDF/索引修复自动变快。

完成条件：问题文件不会拖住快速文件，写回长任务明显减少，取消与退出不残留进程，索引数据语义及既有成功预览不退化。未达到时修复或撤回对应改动；发布与安装包另行执行。
